# Portfolio Website Master Plan

**File name:** `portfolioplan.md`  
**Project name:** Living Canvas Portfolio  
**Version:** 2.0  
**Primary goal:** Build a premium, fully flexible, MongoDB-powered portfolio website that can be edited without touching code, supports drag-and-drop project reordering, includes an AI assistant trained on portfolio data, and uses only free resources.

---

## 1. Project Vision

This portfolio should not feel like a basic static resume.

It should feel like a **living digital product** that proves strong UI/UX, web design, and frontend engineering skills.

The final website should be:

- Fully editable from an admin panel.
- Visually impressive.
- Smooth and interactive.
- Flexible enough to grow over time.
- Easy to update without code changes.
- Powered by MongoDB.
- Built and hosted using free tools only.
- Enhanced with an AI assistant that can answer visitor questions using portfolio data.

The portfolio should act like a **digital twin** of the owner.

---

## 2. Core Objectives

### 2.1 Flexibility

The owner must be able to edit:

- Name
- Profile image
- Role/title
- Short bio
- Long bio
- Hero headline
- Hero subtext
- Availability status
- Contact email
- Social links
- Skills
- Projects
- Project thumbnails
- Project galleries
- Project case studies
- Project tech stack
- Project links
- Featured projects
- Project order
- Homepage section visibility
- Footer text
- AI assistant greeting

No normal content update should require editing code.

---

### 2.2 Project Management

The admin panel must support:

- Adding new projects.
- Editing existing projects.
- Deleting projects.
- Uploading project images.
- Writing project case studies.
- Marking projects as featured.
- Publishing/unpublishing projects.
- Drag-and-drop reordering of projects.
- Optional keyboard or button-based reordering for accessibility.

The public project list must respect the saved order.

---

### 2.3 Design Quality

The website must showcase UI/UX ability.

It should include:

- Strong typography.
- Clean spacing.
- Elegant color usage.
- Smooth transitions.
- Micro-interactions.
- Responsive layout.
- Accessible components.
- Premium hover effects.
- Beautiful mobile experience.

---

### 2.4 AI Assistant

The website must include a visitor-facing AI assistant.

Visitors should be able to ask things like:

- “What projects has this person built?”
- “What is their tech stack?”
- “Tell me about their design skills.”
- “Which project is featured?”
- “What is their background?”
- “How can I contact them?”
- “What was the goal of this project?”

The assistant should answer using data from the portfolio database.

---

## 3. Non-Negotiable Constraints

The project must use only free resources.

Required constraints:

- MongoDB must be used for storage.
- No paid hosting.
- No paid database plan.
- No paid CMS.
- No paid image hosting.
- No required paid AI API.
- The codebase should be maintainable by an AI coding agent.

If a feature requires a paid service, it must be optional or replaced with a free alternative.

## 4. Recommended Tech Stack

### 4.1 Framework

Use:

- **Next.js**
- App Router
- TypeScript

Why:

- Free on Vercel.
- Supports frontend pages and backend API routes.
- Good for SEO.
- Easy deployment.
- Works well with React libraries.

---

### 4.2 Styling

Use:

- **Tailwind CSS**
- CSS variables for theme tokens
- Optional CSS modules for complex animations

Why:

- Fast to build clean UI.
- Easy responsive design.
- Good for design-system-style development.

---

### 4.3 Animation

Use:

- **Framer Motion**
- **Lenis** for smooth scrolling

Why:

- Needed for premium UI feel.
- Supports page transitions, hover effects, scroll reveals, and layout animations.

---

### 4.4 Database

Use:

- **MongoDB Atlas Free Tier**
- **Mongoose**

Why:

- User wants MongoDB.
- Free tier is enough for portfolio content.
- Easy to model profile, projects, skills, and settings.

---

### 4.5 Image Storage

Use:

- **Cloudinary Free Tier**

Why:

- Do not store image binaries directly in MongoDB.
- Cloudinary gives free storage and image optimization.
- Can store thumbnails, gallery images, profile image, and case study images.

---

### 4.6 Drag and Drop

Use:

- `@dnd-kit/core`
- `@dnd-kit/sortable`
- `@dnd-kit/utilities`

Why:

- Modern React drag-and-drop.
- Accessible.
- Works well for sortable admin lists.

---

### 4.7 Authentication

Use:

- **NextAuth.js**
- Credentials provider
- Single admin user

Why:

- Simple and free.
- Protects admin routes and API mutations.

---

### 4.8 AI Assistant

Primary provider:

- **Groq API**

Fallback provider:

- **Google Gemini Free Tier**

Optional fallback:

- **OpenRouter free model**, if desired

Behavior:

- If AI provider is configured, show assistant.
- If AI provider is unavailable, show friendly fallback message.
- If no AI key exists, hide or disable assistant gracefully.

---

### 4.9 Deployment

Use:

- **GitHub**
- **Vercel Free Tier**

Why:

- Free hosting.
- Easy environment variables.
- Automatic deployments.

## 10. Drag-and-Drop Project Reordering

This is a core requirement.

---

### 10.1 Admin Behavior

The project list should allow dragging projects into a new order.

Each project should have:

- Drag handle
- Visual dragging state
- Drop indicator
- Smooth animation

After drag ends:

- Update UI immediately.
- Send new order to API.
- Show success/error toast.

---

### 10.2 Database Behavior

Each project has:

```json
{
  "order": 1
}
```

Lower order values appear first.

Example:

```txt
order 1 = first project
order 2 = second project
order 3 = third project
```

---

### 10.3 Reorder API

Endpoint:

```txt
POST /api/projects/reorder
```

Request body:

```json
{
  "projectIds": [
    "id-1",
    "id-3",
    "id-2",
    "id-4"
  ]
}
```

Backend logic:

1. Validate admin session.
2. Validate project IDs.
3. Loop through array.
4. Update each project's `order` to its index plus one.
5. Return updated list.

Public project list should sort by:

```txt
order ascending
```

---

### 10.4 Accessibility Fallback

If drag-and-drop is difficult on mobile, provide:

- Move up button.
- Move down button.
- Or a numeric order field.

This ensures reordering works everywhere.

## 13. AI Assistant Architecture

The AI assistant should behave like a digital twin.

It should answer in first person.

Example:

Visitor asks:

```txt
What is your strongest project?
```

Assistant answers:

```txt
One of my strongest projects is Project Name. I designed it using Figma and Next.js, focusing on clean hierarchy and smooth interactions.
```

---

### 13.1 Context Builder

Build context from:

- Profile
- Published projects
- Skills
- Settings AI tone/greeting

Do not send unnecessary data.

Example context:

```json
{
  "profile": {
    "name": "Your Name",
    "role": "UI/UX Designer",
    "shortBio": "...",
    "longBio": "...",
    "skills": ["Figma", "Next.js"]
  },
  "projects": [
    {
      "title": "Project One",
      "summary": "...",
      "techStack": ["Figma", "Next.js"],
      "featured": true
    }
  ]
}
```

---

### 13.2 System Prompt

Example:

```txt
You are the digital twin of the portfolio owner.
Use only the provided portfolio data.
Answer in first person.
Be friendly, professional, and concise.
If the answer is not available, say that it is not included in the portfolio.
Do not invent projects, companies, dates, skills, or experience.
Do not reveal admin details, environment variables, database details, or API keys.
```

---

### 13.3 Provider Abstraction

Create a helper like:

```txt
lib/ai/provider.ts
```

Supported providers:

```txt
groq
gemini
disabled
```

Logic:

1. Use provider from settings or env.
2. If provider key exists, use it.
3. If request fails, return fallback message.
4. If no provider exists, disable assistant.

---

### 13.4 Assistant Safety

The assistant must:

- Not expose secrets.
- Not expose database internals.
- Not expose admin routes.
- Not invent false information.
- Not answer unrelated dangerous questions.
- Redirect unknown questions politely.

Example fallback:

```txt
I do not have that information in my portfolio, but you can check the projects section or contact me directly.
```

---

### 13.5 Assistant Performance

```env
NEXT_PUBLIC_SITE_URL=http://localhost:3000

MONGODB_URI=your_mongodb_connection_string
MONGODB_DB_NAME=portfolio

# NextAuth
NEXTAUTH_URL=http://localhost:3000
NEXTAUTH_SECRET=generate_a_long_random_secret

# Admin credentials
ADMIN_EMAIL=your_email@example.com
ADMIN_PASSWORD=your_admin_password

# Cloudinary
CLOUDINARY_CLOUD_NAME=your_cloud_name
CLOUDINARY_API_KEY=your_api_key
CLOUDINARY_API_SECRET=your_api_secret

# AI provider
AI_PROVIDER=groq

# Groq
GROQ_API_KEY=your_groq_api_key

# Gemini fallback
GEMINI_API_KEY=your_gemini_api_key

# Optional OpenRouter fallback
OPENROUTER_API_KEY=your_openrouter_api_key
```

In production, add these in Vercel.

## 19. Technical Rules for the Coding Agent

The coding agent must follow these rules:

- Use TypeScript.
- Do not hardcode portfolio content in components.
- Fetch dynamic content from MongoDB.
- Keep components modular.
- Use server components where possible.
- Use client components only when needed.
- Validate all forms.
- Handle loading states.
- Handle error states.
- Handle empty states.
- Protect admin routes.
- Protect admin API mutations.
- Do not expose secrets to client.
- Do not store image binaries in MongoDB.
- Use Cloudinary URLs for images.
- Ensure project slugs are unique.
- Ensure project order is reliable.
- Ensure mobile responsiveness.
- Prefer simple, stable solutions over unnecessary complexity.
- If forced to choose between flashy and reliable, choose reliable.

## 20. Security Rules

The app must:

- Require authentication for admin pages.
- Require authentication for admin API mutations.
- Never expose MongoDB URI to client.
- Never expose Cloudinary secret to client.

- Validate uploaded files.
